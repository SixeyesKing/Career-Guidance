# AI 职业规划助手项目设计文档

**日期：** 2026-09-30  
**状态：** 早期方案草案；当前 UI 与计划周期以 [已确认 UI 规格](2026-10-01-career-guidance-ui-design.md) 为准  
**项目阶段：** 第八次课程路演前的课程项目版本

## 1. 项目概述

### 1.1 项目定位

AI 职业规划助手面向对就业方向还不清楚的软件工程及相关专业学生。它通过个人画像、岗位介绍、可选体验任务、资料检索和行动计划，帮助用户从“我不知道选什么”走到“我知道接下来可以做什么”。

系统提供信息整理和准备建议，不替用户决定职业，不承诺录用结果。岗位要求和就业信息会因公司、地区和时间变化，系统需要显示资料来源及更新时间；没有可靠资料时明确说明无法确认。

### 1.2 目标用户与示例用户

目标用户为大三、大四软件工程及相关专业学生，尤其是缺少实习经验、对岗位职责和准备方向不熟悉的学生。

第一版路演示例用户：

- 大三软件工程学生；
- 接触过 Java 和 MySQL；
- 做过课程项目；
- 没有实习经历；
- 在后端开发、前端开发和测试开发之间犹豫。

### 1.3 产品目标

用户完成一次使用后，能够：

1. 看懂三个岗位的大致区别；
2. 根据自己的经历选择一个岗位继续了解；
3. 看到个人已有优势和待补能力；
4. 得到带有资料依据、可实际执行的四周准备计划；
5. 保存并导出结果，之后可以修改方向或进展再生成。

### 1.4 产品主线

> 填写个人情况 → 比较岗位 → 可选体验 → 自主选岗 → 查看有依据的分析 → 制定四周行动计划。

## 2. 设计原则

1. **引导探索，不武断推荐。** 用户可以查看岗位比较后自行选择。系统不以单一分数宣布用户“适合”某岗位。
2. **体验任务完全可选。** 用户可以尝试，也可以跳过；跳过不阻断分析流程，也不反复催促。
3. **建议尽量可追溯。** 岗位要求和重要建议应关联知识库来源。示例占位资料必须醒目标明为示例，不能伪装成真实招聘来源。
4. **计划具体可检查。** 行动项写明任务、预计用时和完成标准，避免只输出“提升技术能力”等泛化建议。
5. **先交付闭环，再增加增强项。** 首要目标是路演可稳定完成一次完整流程。

## 3. 第一版范围

### 3.1 第一版包含

- 三个岗位：后端开发、前端开发、测试开发；
- 个人画像填写、修改和保存；
- 三岗位比较卡片；
- 每个岗位一个可选择的短时体验任务；
- 用户自主选择目标岗位；
- 职业分析页面，包含对话、优势、差距、建议行动和来源；
- 固定四周的个性化准备计划；
- 保存画像、对话和计划；
- Markdown 规划方案导出；
- 示例知识资料支持后续替换为核验过的真实资料。

### 3.2 第一版不包含

- 注册、登录和权限管理；
- 全网实时招聘爬取；
- 自动投递简历；
- 薪资预测或就业成功率预测；
- 心理测评或无依据的职业匹配百分比；
- PDF 导出；
- 多岗位的同时深度规划；
- 必须完成体验任务才能查看分析。

这些内容不是第一版验收前置条件。

## 4. 用户流程与页面设计

### 4.1 页面一：个人画像

#### 输入内容

- 年级；
- 专业；
- 已学课程或技术，如 Java、MySQL、HTML/CSS；
- 项目或实习经历；
- 兴趣倾向，如实现功能、制作页面、发现和定位问题；
- 意向城市（可选）；
- 每周可投入的准备时间；
- 当前最困惑的问题（可选）。

#### 交互要求

- 允许用户不知道某项答案，非必要字段可留空；
- 保存后可返回修改；
- 不要求用户先确定目标岗位；
- 明确说明每周可投入时间会用于控制行动计划的任务量。

### 4.2 页面二：岗位探索

页面展示后端开发、前端开发、测试开发三张岗位卡片。每张卡片包含：

- 日常工作；
- 常见技能；
- 与用户当前经历的匹配点；
- 主要能力差距；
- “查看岗位体验任务”入口；
- “选择此岗位继续分析”操作。

匹配点和差距用文字说明，不展示伪精确百分比。

#### 可选体验任务

每个岗位提供一个约 30 至 60 分钟的示例任务：

| 岗位 | 示例任务 | 用户可反馈 |
|---|---|---|
| 后端开发 | 为简单需求设计并实现一个接口，或完成接口逻辑草稿 | 兴趣程度、主观难度、是否愿意继续 |
| 前端开发 | 制作一个简单岗位信息页面，展示基本布局和交互 | 兴趣程度、主观难度、是否愿意继续 |
| 测试开发 | 为给定接口列出测试场景和边界情况 | 兴趣程度、主观难度、是否愿意继续 |

体验任务不是考试，不做自动能力认证。用户可以选择“试做体验任务”或“暂不体验”。若跳过，岗位比较和后续分析继续依据画像、兴趣和知识资料进行。

### 4.3 页面三：职业分析

页面上部显示当前目标岗位，可切换目标并重新分析。主体包含四个区块：

1. **已有优势：** 从用户提供的经历中总结与岗位相关的基础；
2. **待补能力：** 将岗位要求和用户当前信息对照，区分已知差距与信息不足；
3. **建议行动：** 提出可以转成计划任务的下一步；
4. **资料来源：** 展示来源标题、链接和更新时间；占位资料标记为“示例资料”。

同页提供对话咨询：用户可自由提问，也可选快捷问题，例如“这个岗位日常做什么？”“我目前还缺什么？”“下一步可以先做什么？”。

若知识库没有找到支持答案的资料，页面明确说明“暂时没有找到可靠资料依据”，可以继续给出一般性学习建议，但需标识为通用建议或模型建议，不能冒充有来源的事实。

### 4.4 页面四：行动计划

计划周期固定为四周。系统根据画像、选择岗位、能力差距和每周可投入时间调整任务数量及预计时长。

每周任务包含：

- 本周目标；
- 具体任务；
- 预计用时；
- 完成标准；
- 相关知识资料（如有）。

用户可以修改目标岗位或补充进度，再重新生成计划。第一版可提供简单的未开始/进行中/已完成状态；若时间紧，任务状态可列为第二优先级，但计划保存和 Markdown 导出属于闭环要求。

## 5. 内容与知识库设计

### 5.1 示例资料阶段

在真实资料整理完成前，开发可以使用人工编写的示例资料验证程序流程。每条示例必须有 `is_placeholder=true` 或同等标记，并在页面显示“示例资料，仅用于功能演示”。

不得为占位内容生成虚假的公司名称、招聘页面或来源链接。示例资料的来源字段可以写“团队示例内容”，来源链接留空。

### 5.2 后续真实资料格式

每份资料至少包含：

```yaml
title: 后端开发岗位能力要求（示例标题）
job_category: backend
document_type: job_skill
content: 团队整理并核验的资料正文
source_name: 资料来源名称
source_url: https://example.com
published_at: 2026-09
updated_at: 2026-09-30
is_placeholder: false
```

### 5.3 知识类别

- 岗位职责和能力要求；
- 校招、实习和招聘流程；
- 技术学习路径；
- 面试和项目准备；
- 体验任务说明。

首批资料覆盖三个岗位的基础要求即可，资料数量以来源可靠和结构统一为先，不以堆数量为目标。

## 6. 技术架构

### 6.1 技术选型

| 层次 | 技术 | 职责 |
|---|---|---|
| 前端 | Streamlit | 表单、岗位卡片、聊天、计划展示和导出 |
| HTTP 服务 | FastAPI | 接收前端请求并提供画像、分析、对话和计划接口 |
| AI 编排 | LangChain（按需使用） | 组织模型调用、检索上下文和提示词 |
| 关系数据库 | SQLite | 保存画像、会话、体验反馈和计划 |
| 向量检索 | Chroma | 检索就业知识文档片段 |
| 模型服务 | 兼容 OpenAI API 的服务 | 对话和结构化分析生成 |
| 数据访问 | SQLAlchemy 或等价封装 | 隔离业务代码和具体关系数据库 |

SQLite 是第一版选择，不需要独立数据库服务。未来若需要多人并发或远程部署，可以再评估迁移 MySQL。

### 6.2 逻辑组件

```text
Streamlit 页面
  | HTTP/JSON
  v
FastAPI 路由与请求校验
  |------------------------------|
  v                              v
职业服务层                    数据访问层
  |                              |
  +--> RAG 检索服务 --> Chroma   +--> SQLite
  |
  +--> LLM 客户端 --> 模型服务
  |
  +--> 计划生成与 Markdown 导出
```

建议代码按职责组织，不要求一开始引入复杂架构：

```text
app/
  frontend/       Streamlit 页面
  api/            FastAPI 路由和请求模型
  services/       画像、对话、分析、计划业务逻辑
  rag/            文档加载、切分、入库、检索
  db/             SQLite 模型、会话和初始化
  prompts/        模型提示词模板
data/
  knowledge/      Markdown 知识资料
  chroma/         本地向量库数据
exports/          生成的 Markdown 规划
```

### 6.3 运行形态

第一版在开发电脑本地运行：Streamlit 和 FastAPI 分别启动，SQLite 与 Chroma 使用本地持久化目录。模型密钥通过本地 `.env` 配置，不进入源代码、文档、截图或 Git 提交。

## 7. 核心数据模型

以下是逻辑结构，具体字段可由实现阶段按需微调。

### 7.1 `profiles` 用户画像

| 字段 | 用途 |
|---|---|
| `id` | 画像编号 |
| `grade` | 年级 |
| `major` | 专业 |
| `skills_json` | 技术和课程列表 |
| `experience_text` | 项目与实习经历 |
| `interest_json` | 兴趣倾向 |
| `target_city` | 意向城市，可空 |
| `weekly_hours` | 每周准备时间 |
| `updated_at` | 最近更新时间 |

### 7.2 `conversations` 与 `messages`

`conversations` 保存会话编号、关联画像、当前岗位和创建时间。`messages` 保存会话编号、角色（user/assistant）、正文、创建时间，以及可选的引用来源 JSON。

### 7.3 `experience_feedback`

保存体验任务编号、岗位类别、用户是否开始/跳过、兴趣反馈、难度反馈和是否愿意继续。跳过任务时不要求填写反馈。

### 7.4 `analyses`

保存关联画像和目标岗位、优势、差距、建议行动、引用来源、生成时间。重新分析时创建新版本或明确覆盖规则，避免页面展示旧分析。

### 7.5 `plans` 与 `plan_tasks`

`plans` 保存画像、目标岗位、四周计划正文或结构化数据、版本和创建时间。`plan_tasks` 可选，用于逐周保存目标、任务、预计用时、完成标准和状态。若第一版不做任务状态，可以先将四周计划作为 JSON 保存于 `plans`。

### 7.6 向量文档元数据

Chroma 文档片段元数据至少包含 `document_id`、`title`、`job_category`、`document_type`、`source_name`、`source_url`、`updated_at` 和 `is_placeholder`，确保引用信息能随检索结果返回。

## 8. 核心接口草案

接口命名可在实现时调整，但前后端需先约定请求和响应格式。

| 方法与路径 | 用途 |
|---|---|
| `GET /health` | 检查后端是否可用 |
| `GET /jobs` | 获取三个岗位介绍和能力维度 |
| `GET /profiles/{id}` | 读取画像 |
| `POST /profiles` | 创建画像 |
| `PUT /profiles/{id}` | 修改画像 |
| `POST /experience-feedback` | 保存体验任务选择或反馈 |
| `POST /analysis` | 生成指定岗位分析 |
| `POST /chat` | 对话咨询并返回回答和来源 |
| `POST /plans` | 生成并保存四周计划 |
| `GET /plans/{id}` | 读取已保存计划 |
| `GET /plans/{id}/export` | 导出 Markdown |

对话响应示例：

```json
{
  "answer": "结合你填写的经历……",
  "sources": [
    {
      "title": "后端开发岗位能力要求",
      "source_name": "团队示例内容",
      "source_url": null,
      "updated_at": "2026-09-30",
      "is_placeholder": true
    }
  ],
  "grounding_status": "placeholder"
}
```

`grounding_status` 用于区分真实来源、示例资料、无检索依据等状态，前端按状态展示提示。

## 9. 关键数据流

### 9.1 对话问答

1. 前端提交问题、画像编号、会话编号和当前岗位；
2. 后端校验输入并读取画像与近期对话；
3. 检索服务根据问题和岗位从 Chroma 取回相关片段；
4. 后端把问题、画像、资料片段和回答约束交给模型；
5. 后端保存用户消息、助手回答和引用元数据；
6. 前端显示回答、引用资料和资料状态。

### 9.2 岗位分析

1. 读取画像和指定岗位的能力模型；
2. 检索岗位相关知识；
3. 生成结构化的优势、差距和行动建议；
4. 保存分析结果及来源；
5. 前端展示并允许用户切换岗位重新分析。

### 9.3 四周计划

1. 读取最新画像、目标岗位、分析结果和每周时间预算；
2. 将差距转为有完成标准的任务；
3. 检查任务数量和预计时间不超过用户给定预算；
4. 保存计划；
5. 前端展示并提供 Markdown 导出。

## 10. 生成规则与质量约束

### 10.1 职业分析输出

使用固定字段而不是只生成一段长文本：

```json
{
  "strengths": [],
  "gaps": [],
  "actions": [],
  "sources": [],
  "uncertainties": []
}
```

用户没有提供足够信息时，将内容列入 `uncertainties` 或提出一个简短追问，不把未知情况当成事实。

### 10.2 岗位比较

比较内容固定为日常工作、常见技能、与当前经历的匹配点、主要能力差距。第一版不输出百分比、排名或录用概率。

### 10.3 行动计划

- 每周任务数量要符合用户的时间预算；
- 每项任务包含可观察的完成标准；
- 任务应对应分析中发现的差距；
- 计划中的招聘时点或政策信息必须有来源及时间信息；
- 若计划依赖未知信息，标明假设或先询问用户。

## 11. 异常处理

| 情况 | 系统行为 |
|---|---|
| 必填信息缺失 | 指出缺少项，允许先保存部分画像；必要时一次追问一个问题 |
| 未检索到相关资料 | 明确显示无可靠依据，不伪造引用；允许提供标明为一般建议的内容 |
| 使用的是占位资料 | 显示“示例资料，仅用于演示”，不伪造来源链接 |
| 模型 API 超时或密钥错误 | 页面展示可理解的失败信息；保留已输入内容，允许重试 |
| SQLite 或 Chroma 文件不可用 | 后端记录可诊断错误；前端提示本地数据服务不可用 |
| 模型返回格式不符合约定 | 尝试一次格式修复或返回受控错误，不把异常原文直接展示 |
| 用户切换目标岗位 | 重新生成对应分析；旧对话和旧计划仍保留并标记所属岗位 |

## 12. 安全与隐私

- `.env` 仅保存在开发电脑，并加入 `.gitignore`；
- 仓库只提交 `.env.example`，内容为占位值；
- 不在日志和路演截图中打印 API 密钥；
- 第一版不采集身份证、手机号等非必要敏感信息；
- 用户画像只收集完成规划所需的信息；
- 如果使用外部模型服务，不将真实个人隐私或未经允许的简历内容提交给模型。

## 13. 验收场景

### 场景 A：跳过体验任务

用户填写画像后查看三个岗位，选择“暂不体验”，仍能看到岗位对比并选择后端开发继续分析。

**通过条件：** 跳过不会阻断流程，也不会强制评分或反复弹窗。

### 场景 B：参加体验任务

用户打开测试开发任务，提交兴趣和难度反馈，之后选择测试开发进行分析。

**通过条件：** 反馈被保存，分析可以把它作为用户自述信息之一；系统不宣称体验结果等于专业能力认证。

### 场景 C：查看来源

用户询问某岗位常见技能，系统返回回答和来源状态。

**通过条件：** 真实资料展示标题、链接和更新时间；占位内容明确显示为示例；无来源时明确告知。

### 场景 D：生成四周计划

用户每周填写 5 小时，选择目标岗位后生成计划。

**通过条件：** 输出四周目标、任务、预计用时和完成标准，任务与分析差距关联，预计工作量尽量不超过时间预算。

### 场景 E：保存和导出

用户关闭并重新打开程序后读取画像和计划，再导出 Markdown。

**通过条件：** SQLite 中的数据可重新读取，导出文件结构清楚且引用状态保留。

### 场景 F：服务异常

模型 API 无法访问或检索为空。

**通过条件：** 页面保留输入并显示明确错误或无依据提示，不出现堆栈信息或虚假来源。

## 14. 开发顺序建议

1. 先搭建页面和 FastAPI 健康检查；

4. 接入模型服务并保护密钥；
5. 建立示例知识库和 Chroma 入库流程；
